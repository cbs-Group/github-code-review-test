Customize Copilot reviews

Tell Copilot what matters in your codebase, choose how deep it looks, and decide when it runs.

A path-specific file starts with front matter:

---
applyTo: "**/*.test.ts"
# optional: hide this file from code review or from the cloud agent
# excludeAgent: "code-review"
---

- Tests must be deterministic: no real network, no real clock.

Writing good review instructions

  • Write short, concrete, checkable rules (“Money is an integer number of cents”) instead of general wishes (“write good code”).
  • Say what to prioritize and what to skip, for example formatter-level style.
  • Specify the comment format you want, such as severity tags.
  • Instructions are read from the pull request's head branch, so you can try changes in a pull request before merging them.
  • Repository admins can turn off custom instructions for code review in Settings → Copilot → Code review.

Review effort

LevelUse for
LiteStandard review, lowest cost
Balanced (default)Deeper analysis of complex logic, security-sensitive code, and cross-service changes
MaxMost intensive review with multiple high-reasoning models, for changes that need the most scrutiny

Set it per request under Reviewers, as a personal default in your Copilot settings, or as the repository default for automatic reviews. Organizations and enterprises can cap the maximum level. Higher levels use more AI credits.

When Copilot runs

  • Manual: choose Copilot under Reviewers. Good for selective use.
  • Automatic for your own pull requests: personal Copilot settings → Code review.
  • Automatic for a repository or organization: a ruleset with Automatically request Copilot code review, optionally with Review new pushes and Review draft pull requests.

Without Review new pushes, Copilot reviews a pull request once; request a re-review manually after larger changes.

Limits and good practice

  • Copilot can miss issues and can produce false positives. Treat comments as suggestions and keep human review.
  • By default Copilot does not approve or block a pull request; approvals must be enabled explicitly by an admin.
  • Small, focused pull requests get better reviews and cost less.
  • Rate comments with 👍 / 👎 to send feedback to GitHub.
  • Pull requests opened by bots are billed to the organization; plan budgets accordingly.
